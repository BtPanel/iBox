# 直播播放稳定性第一阶段设计

## 背景

当前直播播放由手机和 TV 两个 `LiveActivity` 共用 `LivePlaybackController`。现有控制器在任何播放错误后，都会先按固定间隔重连当前线路最多三次，再按线路原始顺序切换。这个行为有三个问题：

1. 解析失败、空地址等确定性错误仍会重复请求同一线路，恢复慢。
2. 失败只按频道记录，无法识别同一频道中哪条线路更可靠，也无法利用历史启动速度。
3. 播放器只把错误文案传到直播控制器，超时、网络、解析和解码错误到达策略层前已失去类型信息。

第一阶段只解决播放连接与故障恢复。目标是在不改变直播源格式、不引入新设置项的前提下，让应用更快避开坏线路，并让用户清楚看到连接、重连和换线进度。

## 范围

本阶段包含：

- 按“直播源 + 频道 + 线路 URL”记录线路健康，不再用频道级失败记录指导线路选择。
- 将播放失败结构化分类，并让播放器、播放服务和直播控制器之间保留失败类型。
- 根据失败类型决定重试当前线路、切换健康线路或结束恢复。
- 保持用户手动选线的优先级。
- 在手机和 TV 端统一展示连接、重连、换线、播放成功和最终失败状态。
- 为分类、评分、冷却、恢复状态机和双端集成增加回归测试。

本阶段不包含：

- 频道列表、收藏、搜索和 EPG 交互重做。
- 直播源测速入口、批量检测或线路健康管理页面。
- 节目录制、客户端缓存时移或后台下载。
- 新增自动换线、重连次数等用户设置。
- 修改点播的换线和换源策略。

## 设计原则

- Activity 负责输入和展示，恢复规则只存在于共用播放层。
- 失败类型来自结构化信号，不解析本地化错误文案。
- 一次恢复周期中每条线路最多自动尝试一次，明确允许的同线快速重试除外，不能循环切线。
- 用户主动选择优先于历史评分；只有该线路实际失败后，自动策略才可以离开它。
- 所有延迟任务和异步回调都绑定当前请求，切频道、手动选线、退出页面或重置后不得影响新会话。
- 不持久化完整播放 URL，避免把带令牌或私人地址写入偏好设置。

## 模块边界

### `PlaybackFailure`

播放器层新增不可变失败对象，至少包含：

- `kind`：失败分类。
- `message`：供最终错误 UI 和诊断页使用的现有文案。
- `errorCode`：底层存在稳定错误码时保留，否则为空。

`PlayerManager.Callback`、`PlaybackService.PlayerCallback` 和 `PlaybackActivity` 增加结构化错误通道。旧的字符串错误入口保留为兼容委托，点播等现有调用方继续得到相同文案，不要求同步采用直播恢复策略。

### `LiveFailureClassifier`

纯策略类，将播放解析结果和 `PlaybackFailure` 映射为 `LiveFailureKind`。它不访问 UI、播放器实例或持久化数据，可直接进行 JVM 单元测试。

### `LiveLineKey` 与 `LiveLineHealth`

`LiveLineKey` 使用以下稳定字段：

- 当前直播源标识：沿用 `LiveChannelStore` 的源名称与配置 URL 哈希。
- 分组名和频道名：防止不同分组中的同名频道互相污染。
- 规范化线路 URL 的 SHA-256：移除 `$线路名` 后缀，保留决定实际请求的 URL 内容，仅存哈希。

`LiveLineHealth` 保存：成功次数、失败次数、连续失败次数、最近成功时间、最近失败时间、平均启动耗时和冷却截止时间。成功与失败计数均封顶 20，避免历史样本永久压过近期表现。

### `LiveLineHealthStore`

负责加载、容错、裁剪和保存线路健康记录，并提供“按健康度排序候选线路”的单一入口。存储实现位于共用层，使用独立版本化偏好键，不让控制器直接处理 JSON。

### `LiveRecoveryPolicy`

输入当前失败类型、当前线路、候选线路健康状态、本次恢复周期已尝试集合以及现有直播设置，输出以下一种决定：

- `RETRY_CURRENT(delayMs)`
- `SWITCH_LINE(targetIndex)`
- `FAIL`

策略本身不执行播放、不修改 `Channel`，因此可覆盖完整决策矩阵。

### `LivePlaybackController`

保留现有频道、回看、EPG 和播放请求职责，并作为第一阶段的会话协调器：

- 为每个直播请求建立递增的请求代号和恢复周期。
- 记录连接开始时间、已尝试线路和当前线路是否由用户手动选择。
- 调用分类器、健康存储和恢复策略。
- 输出统一的 `LiveConnectionState` 给 Host。

不再新建与 `LivePlaybackController` 职责重叠的 `LiveSession`。这样可以增加明确的策略边界，同时控制对现有手机、TV 和回看流程的改动范围。

## 失败分类

`LiveFailureKind` 定义五类：

| 类型 | 来源 | 默认处理 |
| --- | --- | --- |
| `SOURCE` | URL 解析返回错误、最终 URL 为空、格式或 DRM 前置校验失败 | 不重试当前线路，直接换线 |
| `NETWORK` | DNS、连接、HTTP、连接重置和常规 I/O 失败 | 当前线路快速重试一次，再换线 |
| `TIMEOUT` | 播放启动超时或底层明确的超时错误码 | 当前线路快速重试一次，再换线 |
| `DECODE` | 播放器完成既有软硬解切换后仍失败 | 不再由控制器同线重试，直接换线 |
| `PLAYBACK` | 无法可靠归入以上类型的致命播放错误 | 当前线路快速重试一次，再换线 |

错误处理顺序固定为：播放器引擎内部恢复、播放器软硬解恢复、直播恢复策略。只有前两层均未恢复时，错误才进入 `LiveRecoveryPolicy`，防止控制器和播放器同时重试。

回看请求继续沿用当前行为，不参与直播线路评分和自动换线，避免直播 URL 与带时间参数的回看 URL 相互污染。

## 健康评分与冷却

候选线路先按资格过滤，再按分数排序。

### 资格过滤

1. 排除本次恢复周期已经尝试过的线路。
2. 正常情况下排除仍在冷却期的线路。
3. 若所有未尝试线路都在冷却期，允许从中选择分数最高的一条，避免因旧记录导致频道完全无法播放。
4. 分数相同则保持直播源中的原始线路顺序，保证行为可预测。

### 分数

基础分为 100，使用以下有限权重：

```text
score = 100
      + min(successCount, 5) * 4
      - min(failureCount, 5) * 4
      - min(consecutiveFailures, 3) * 25
      - startupPenalty
```

`startupPenalty` 根据平均启动耗时计算：2 秒内为 0 分，之后每多 1 秒扣 1 分，最多扣 20 分。评分只用于同一频道的线路排序，不跨频道比较。

### 冷却

每次最终落到线路级失败时更新连续失败次数，并按失败类型设置基础冷却：

| 类型 | 基础冷却 |
| --- | --- |
| `SOURCE` | 30 分钟 |
| `NETWORK` | 2 分钟 |
| `TIMEOUT` | 2 分钟 |
| `DECODE` | 10 分钟 |
| `PLAYBACK` | 5 分钟 |

实际冷却时间为 `基础冷却 * 2^(连续失败次数 - 1)`，指数最多取 3，单次冷却最长不超过 24 小时。允许的同线快速重试失败后才结束该线路尝试并写入冷却；第一次失败会更新诊断计数，但不会在重试前阻止当前线路。

播放器进入 READY 后开始计时。连续播放满 30 秒视为稳定成功：成功次数加一、连续失败清零、冷却清零，并用指数移动平均更新启动耗时，首个样本直接采用实际耗时，后续使用 `新平均值 = 旧值 * 0.7 + 新样本 * 0.3`。READY 后不足 30 秒再次失败仍按失败处理，不记成功。

健康记录 30 天没有成功或失败活动时删除；每个直播源最多保留 500 条记录，超出时优先删除最久未活动的记录。

## 恢复规则

一次恢复周期从用户选择频道、手动选择线路或主动刷新开始，在稳定播放 30 秒、切换频道、离开页面或最终失败时结束。

1. 用户进入一个频道时，从该频道可用线路中选择健康分最高的线路；没有健康记录时保持源内原始顺序。用户主动刷新继续使用当前线路，不因评分切线。
2. 用户手动选线时直接使用目标线路，即使它正在冷却，也允许本周期尝试一次。
3. `NETWORK`、`TIMEOUT`、`PLAYBACK` 在“自动重连”开启时，对当前线路最多快速重试一次；延迟沿用现有重连秒数设置。设置为关闭时跳过同线重试。
4. `SOURCE` 和播放器已穷尽软硬解恢复后的 `DECODE` 不做控制器级同线重试。
5. 当前线路结束尝试后，若“自动换线路”开启，从未尝试候选中选择健康分最高的线路。关闭时直接进入最终失败。
6. 每个候选线路应用同样规则，但同一恢复周期不得回到已经尝试的线路。
7. 没有候选线路时显示最后一次失败文案，并把频道标为失败；稳定播放后清除频道失败标记。
8. 用户在倒计时或换线期间手动选频道、线路或刷新时，立即取消旧任务并开始新周期。旧请求返回时因请求代号不匹配而被忽略。

现有设置语义保持不变：“自动重连”只控制同线重试，“自动换线路”只控制换线。两项均关闭时，第一次未被播放器内部恢复的错误直接显示失败。

## 手动选线

- 用户点击某条线路后，该线路成为当前频道本次会话的手动首选，历史低分和冷却不能阻止这次请求。
- 自动策略不能因为其他线路评分更高而主动离开手动线路；只有收到实际失败后才执行恢复。
- 手动线路失败并自动切走后，本恢复周期不再自动切回。用户再次手动选择它会建立新周期，并再次允许一次明确尝试。
- 切换频道会清除前一频道的会话级手动标记；再次进入该频道时按健康分重新选择初始线路，并同步更新频道对象的线路索引。

## 连接状态与双端展示

新增不可变 `LiveConnectionState`：

| 状态 | 展示 |
| --- | --- |
| `CONNECTING(line, total)` | 现有加载区域显示“正在连接 线路 x/y” |
| `RECONNECTING(line, attempt, delay)` | 同一区域显示“播放中断，n 秒后重连” |
| `SWITCHING(from, to, total)` | 同一区域显示“线路 x 不可用，正在切换到线路 y” |
| `PLAYING(line, total)` | 清除恢复文案和加载遮罩，更新当前线路选择 |
| `FAILED(message)` | 显示现有最终错误与重试入口 |

手机和 TV 的 `LiveActivity` 通过 `LivePlaybackHost.renderConnectionState` 使用同一语义状态和字符串资源。状态在现有播放器状态区域原位更新，不新增弹窗，不使用位移动画，也不反复隐藏、创建视图；仅使用现有统一的短淡入淡出，避免恢复期间闪屏。

无障碍播报只在状态类别改变时触发，倒计时逐秒更新不重复播报。TV 切线期间保持当前播放器区域焦点，不抢走频道或控制栏焦点。

## 持久化与升级兼容

- 新数据写入 `live_line_health_v2_<sourceKey>`，JSON 顶层包含版本号和记录列表。
- URL 只作为计算 SHA-256 的输入，不写入偏好值；记录中保存 URL 哈希。
- 加载时遇到空值、旧版本、字段缺失、非法数字或损坏 JSON，丢弃对应记录并返回可用部分，不让异常进入 Activity。
- 现有 `live_failed_<sourceKey>` 继续只负责频道列表的失败标记：所有线路恢复耗尽时写入，任一线路稳定播放后清除。它不参与线路排序，因此无需把频道级数据猜测迁移到某条线路。
- 现有最近观看、收藏、频道线路索引和直播设置键均不变。

## 数据流

```text
用户选台/选线
    -> LivePlaybackController 开始恢复周期并发布 CONNECTING
    -> LiveViewModel 解析实际地址
    -> PlayerManager / PlaybackService 播放
        -> READY：发布 PLAYING，30 秒后记录稳定成功
        -> 内部可恢复错误：播放器自行恢复
        -> 最终错误：PlaybackFailure
            -> LiveFailureClassifier
            -> LiveRecoveryPolicy
                -> RETRY_CURRENT：发布 RECONNECTING
                -> SWITCH_LINE：记录失败并发布 SWITCHING
                -> FAIL：记录失败并发布 FAILED
```

解析请求和播放请求都携带当前请求代号。Controller 在应用结果、执行延迟任务和记录健康数据前再次校验代号及频道/线路，确保迟到回调不会污染新线路。

## 测试方案

### JVM 单元测试

- `LiveFailureClassifierTest`
  - 空 URL、解析失败、超时、网络 I/O、解码穷尽和未知 Fatal 的分类。
  - 分类不依赖中英文错误文本。
- `LiveLineHealthTest`
  - 分数边界、计数封顶、启动耗时惩罚、稳定成功清除连续失败。
  - 各错误类型冷却、指数上限和 24 小时总上限。
- `LiveLineHealthStoreTest`
  - 不同源、分组、频道和 URL 不串数据。
  - URL 未明文持久化。
  - 损坏 JSON、未知版本、30 天过期和 500 条裁剪。
- `LiveRecoveryPolicyTest`
  - 五类失败的重试/换线矩阵。
  - 两项设置分别关闭及同时关闭。
  - 冷却过滤、全部冷却回退、分数相同保持原顺序。
  - 手动线路绕过一次冷却、失败后不自动回跳。
- `LivePlaybackControllerTest`
  - 每线路最多一次快速重试、恢复周期不循环。
  - 切频道、手动选线、刷新和 reset 取消旧任务。
  - 迟到解析/播放回调被忽略。
  - READY 不足 30 秒不记成功，满 30 秒记录成功。
  - 回看错误不写直播线路健康数据。

纯策略对象注入时钟与调度器，测试不依赖真实等待。健康存储通过可替换的键值接口测试序列化，Android `Prefers` 适配只做薄封装。

### 构建与设备验证

- 四个 Debug 变体 JVM 单元测试全部通过。
- 手机 arm64 与 TV arm64 Debug 编译、Lint 通过；合并前再覆盖四个 Debug 构建。
- 手机和 TV 各用至少一个双线路测试频道验证：
  - 第一线路空 URL/解析失败时立即切线。
  - 第一线路超时时只重试一次，然后切到健康线路。
  - 手动选回低分线路时能够播放尝试，不会被评分立即切走。
  - 恢复期间切频道，旧倒计时和旧回调不影响新频道。
  - 自动重连、自动换线分别关闭时行为与设置一致。
  - 日间/夜间、手机横竖屏和 TV 遥控器焦点下状态文案清晰且无闪屏。

## 验收标准

1. 解析或空 URL 错误不再对同一线路做无意义重连。
2. 网络、超时和未知播放错误每条线路最多自动快速重试一次；一次恢复周期不会循环访问已失败线路。
3. 同一频道再次进入时，近期稳定且启动更快的线路优先于近期连续失败线路，但手动选线始终先尝试。
4. 用户能在手机和 TV 上区分正在连接、等待重连、自动换线和最终失败，状态切换不产生弹窗或页面闪烁。
5. 切频道、手动选线、刷新或退出后，不会发生旧任务触发的回跳、错误覆盖或健康数据误记。
6. 老版本升级后最近观看、收藏、频道失败标记和直播设置均保留；损坏或未知健康数据不会导致崩溃。
7. 点播播放错误提示与恢复行为无回归，回看播放不参与直播线路评分。
